## Context

**当前状态**：
- `dividend-yield-calculator` skill 使用硬编码的 mock 数据
- 无统一的数据获取层
- 无缓存机制，每次计算都需要重新获取数据
- 数据格式不统一

**约束条件**：
- 必须使用 baostock 作为数据源（免费、无需注册）
- 需要考虑 API 调用频率限制
- 数据需要本地持久化缓存

**利益相关者**：
- FinAgent 用户：需要真实、准确的股票数据进行分析
- 开发者：需要易于扩展和维护的代码结构

## Goals / Non-Goals

**Goals：**
- 构建可扩展的股票数据提供者架构
- 实现 baostock 数据源集成
- 提供本地缓存机制，减少 API 调用
- 标准化股票数据模型
- 支持 `dividend-yield-calculator` 切换到真实数据

**Non-Goals：**
- 实现完整的选股策略引擎（留待后续）
- 实时行情推送（目前仅支持历史数据查询）
- 多数据源聚合（初期仅支持 baostock）
- 复杂的缓存失效策略（初期使用简单 TTL）

## Decisions

### 1. 架构模式：Provider 模式

**决策**：使用 Provider 抽象层封装数据源

**理由**：
- 支持未来扩展其他数据源（tushare、akshare 等）
- 上层应用无需关心具体数据源实现
- 便于单元测试（可 mock provider）

**备选方案**：
- 直接在 skill 中调用 baostock API（被否决：耦合度高，难以扩展）
- 使用 Facade 模式（被否决：Provider 模式更适合多数据源场景）

### 2. 缓存方案：SQLite 本地缓存

**决策**：使用 SQLite 作为本地缓存存储

**理由**：
- 无需额外依赖，Python 内置支持
- 支持结构化查询，便于数据检索
- 轻量级，适合个人工具场景
- 支持事务，保证数据一致性

**备选方案**：
- Redis（被否决：需要额外服务，增加复杂度）
- 文件缓存 JSON（被否决：查询效率低，不支持结构化检索）
- 不使用缓存（被否决：baostock 有频率限制，必须缓存）

### 3. 数据模型：基于 pandas.DataFrame

**决策**：使用 pandas.DataFrame 作为核心数据结构

**理由**：
- baostock SDK 原生返回 DataFrame
- 金融数据分析标准工具
- 便于数据转换和计算
- 支持多种导出格式

**备选方案**：
- 自定义数据类（被否决：重复造轮，失去 pandas 生态优势）
- 纯字典/列表（被否决：类型不安全，缺乏计算能力）

### 4. API 频率控制：速率限制器

**决策**：实现简单的速率限制器，控制 baostock API 调用频率

**理由**：
- baostock 有频率限制（建议每秒不超过 1 次请求）
- 避免被封禁 IP
- 提供友好的错误提示

**备选方案**：
- 不限制（被否决：可能被封禁）
- 使用第三方限流库（被否决：简单场景无需额外依赖）

### 5. 目录结构

**决策**：在项目根目录创建 `finagent/` 作为 Python 包

```
finagent/
├── __init__.py
├── data/
│   ├── __init__.py
│   ├── models/           # 数据模型定义
│   │   ├── __init__.py
│   │   └── stock.py      # 股票数据模型
│   ├── providers/        # 数据提供者
│   │   ├── __init__.py
│   │   ├── base.py       # Provider 基类
│   │   └── baostock.py   # baostock 实现
│   ├── cache/            # 缓存层
│   │   ├── __init__.py
│   │   └── sqlite.py     # SQLite 缓存实现
│   └── client.py         # 数据客户端入口
└── utils/
    ├── __init__.py
    └── rate_limiter.py   # 速率限制器
```

**理由**：
- 清晰的分层结构
- 便于扩展和维护
- 符合 Python 包最佳实践

## Risks / Trade-offs

| 风险 | 缓解措施 |
|------|----------|
| baostock 服务不稳定 | 实现重试机制和错误处理；提供缓存降级 |
| API 频率限制导致性能问题 | 实现批量查询接口；优先使用缓存 |
| 数据格式变化 | 使用版本化的数据模型；添加单元测试 |
| 缓存数据过期 | 实现可配置的 TTL；提供手动刷新接口 |
| 股票代码变化 | 提供股票列表更新接口；定期同步股票列表 |

**Trade-offs**：
- **简单性 vs 功能完整性**：优先选择简单方案，避免过度设计
- **性能 vs 准确性**：缓存提高性能但可能牺牲实时性（金融场景可接受）
- **扩展性 vs 开发速度**：Provider 模式增加代码量但提高可扩展性

## Open Questions

1. **缓存 TTL 设置**：不同数据类型的缓存有效期？
   - 股票基本信息：较长（如 30 天）
   - 历史行情数据：中等（如 7 天）
   - 财务数据：较短（如 1 天）
   - *决策：实现可配置 TTL，默认值按上述建议*

2. **错误处理策略**：baostock API 失败时的行为？
   - 抛出异常让上层处理
   - 返回空数据
   - 使用缓存数据（降级）
   - *决策：实现降级机制，优先使用缓存，记录日志*

3. **并发访问**：是否需要支持多线程安全？
   - SQLite 默认支持多线程
   - baostock SDK 是否线程安全？
   - *决策：初期单线程，后续按需优化*
